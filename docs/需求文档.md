## 1. 项目概述

### 1.1 项目目标

构建一个可编辑内容的**活码管理系统**。用户创建文章内容，为文章生成多个固定二维码（活码），二维码印到物料上后不可更改，但后台可随时修改文章内容或调整跳转目标。每个活码独立统计扫码数据，支持按天趋势查看和导出。

### 1.2 核心流程

```
用户创建文章（标题+富文本+图片）
       ↓
文章内容定稿 → 页面发布（自动获得平台页面URL）
       ↓
为文章生成活码（一个或多个） → 每个活码获得唯一ID
       ↓
生成二维码（含Logo、边框文字、尺寸可选）
       ↓
下载二维码 → 印到海报/名片/包装等物料上
       ↓
用户扫码 → 跳转到平台文章展示页 → 阅读内容
       ↓
后台实时统计扫码数据（总量+趋势+导出）
```

### 1.3 核心原则

- **二维码固定，内容可变**：印出去的二维码永远不变，后台随时改内容
- **先内容后活码**：先有文章，再按需生成活码
- **一对多**：一篇文章可生成多个活码，每个活码独立统计
- **扩展优先**：所有核心模块预留接口，后续加功能不改表结构

## 2. 核心概念与数据模型

### 2.1 概念定义

| 概念 | 定义 | 示例 |
|------|------|------|
| 文章（Article） | 可编辑的内容单元，是系统的核心载体 | 产品介绍、活动公告、企业信息 |
| 活码（LiveCode） | 固定标识符，指向一篇文章，可独立统计 | 活码ID: `a3kF9q` |
| 二维码（QRCode） | 存活码跳转 URL 的二维码图片 | 扫描后跳 `https://域名/l/a3kF9q` |
| 扫码记录（ScanLog） | 每次扫码的日志，用于统计 | 时间、活码ID、IP、设备等 |

### 2.2 关系图

```
文章 (Article)      活码 (LiveCode)       扫码记录 (ScanLog)
┌──────────┐        ┌─────────────┐       ┌──────────────┐
│ id       │ 1──N→  │ id          │ 1──N→ │ id           │
│ title    │        │ code        │       │ live_code_id │
│ content  │        │ article_id  │       │ scanned_at   │
│ images   │        │ is_active   │       │ ip_address   │
│ status   │        │ created_at  │       │ user_agent   │
│ extra_fields│     │ qr_config   │       │ extra_data   │
│ created_at │      │ scan_count  │       └──────────────┘
│ updated_at │      │             │
└──────────┘        └─────────────┘
```

### 2.3 字段详细说明

#### Article（文章）

| 字段 | 类型 | 说明 |
|------|------|------|
| `id` | Integer, PK | 自增主键 |
| `title` | String(200) | 文章标题 |
| `content` | Text | 富文本 HTML 正文 |
| `images` | JSON | 图片 URL 列表，第一张为封面图 |
| `status` | Enum(draft, published) | 发布状态，默认草稿 |
| `extra_fields` | JSON | **扩展字段**，用于后续插件（地图、商品、文件等） |
| `created_at` | DateTime | 创建时间 |
| `updated_at` | DateTime | 更新时间 |
| `author_id` | Integer, FK | 预留多用户：作者 ID（第一版可为 null） |

#### LiveCode（活码）

| 字段 | 类型 | 说明 |
|------|------|------|
| `id` | Integer, PK | 自增主键 |
| `code` | String(16), Unique | 活码标识符，随机字符串（如 `a3kF9q`） |
| `article_id` | Integer, FK → Article | 关联的文章 |
| `is_active` | Boolean | 是否启用，默认 True |
| `created_at` | DateTime | 创建时间 |
| `qr_config` | JSON | 二维码生成配置（尺寸、Logo路径、边框文字），见 4.3 节 |
| `scan_count` | Integer | 扫码总量（缓存字段，用于快速展示） |
| `extra_data` | JSON | 预留扩展字段 |

#### ScanLog（扫码记录）

| 字段 | 类型 | 说明 |
|------|------|------|
| `id` | BigInteger, PK | 自增主键 |
| `live_code_id` | Integer, FK → LiveCode | 活码ID |
| `scanned_at` | DateTime | 扫码时间，索引 |
| `ip_address` | String(45) | 请求 IP（预留） |
| `user_agent` | String(500) | 设备信息（预留） |
| `referer` | String(500) | 来源（预留） |
| `extra_data` | JSON | 预留扩展字段（后续设备/地域分析） |

## 3. 技术栈

### 3.1 已确认技术栈

| 模块 | 技术 | 说明 |
|------|------|------|
| 后端 API | FastAPI | 异步框架，自动生成 API 文档 |
| ORM | SQLAlchemy 2.0 | 异步支持，JSON 字段原生支持 |
| 数据库迁移 | Alembic | 版本化管理数据库变更 |
| 数据库（第一版） | SQLite | 零配置，单文件，无需安装数据库服务 |
| 数据库（后续可升） | PostgreSQL | 改一行配置即可迁移 |
| 后台管理界面 | SQLAdmin | 文章/活码 CRUD 自动生成 |
| 自定义页面 | Jinja2 + HTMX | 统计图表、二维码生成、批量下载等 |
| 统计图表 | Chart.js | 轻量 JavaScript 图表库 |
| 富文本编辑器 | Quill | 轻量、无框架依赖，适配 Jinja2 模板 |
| 二维码生成 | qrcode + Pillow | 后端生成，Logo/边框文字用 Pillow 叠加 |
| ZIP 打包 | Python zipfile | 标准库，批量下载用 |

### 4.2 活码管理模块

#### 功能列表

| 功能 | 说明 | 第一版 |
|------|------|--------|
| 生成活码 | 为指定文章生成一个活码（随机ID） | ✅ |
| 停用/启用活码 | 停用后扫码跳转 404 或提示页 | ✅ |
| 删除活码 | 软删除 | ✅ |
| 活码列表 | 按文章/状态筛选，显示扫码量 | ✅（SQLAdmin） |
| 活码详情页 | 展示基本信息、二维码预览、扫码统计 | ✅（自定义页面） |

#### 活码跳转流程

```
用户扫码 → 浏览器打开 https://域名/l/a3kF9q
              ↓
FastAPI 路由 /l/{code} 接收请求
              ↓
查询 LiveCode 表 → 找到关联的 Article
              ↓
（预留：权限校验 → 密码验证 → 跳转目标判断）
              ↓
记录 ScanLog（扫码时间、IP、设备等）
              ↓
返回文章展示页（或 404/停用提示）
```

#### 活码ID生成规则

- 随机字符串，长度 8 位（大小写字母 + 数字，如 `a3kF9qXz`）
- 唯一索引，碰撞检测
- 后续扩展：支持自定义别名

## 7. 非功能需求

### 7.1 性能 (Performance)

| 需求 | 指标 | 说明 |
|------|------|------|
| 扫码跳转响应 | < 500ms（P99） | 用户扫码后到页面展示的延迟，含数据库查询+日志写入 |
| 二维码生成 | < 2s/张（含Logo+边框文字） | 后台生成二维码图片的耗时 |
| 批量生成（50个） | < 30s | 批量生成+ZIP打包的总耗时 |
| 统计查询（近30天） | < 1s | 图表数据加载时间 |
| 并发扫码 | 支持 100 QPS（第一版） | 本地运行时不因多用户扫码而卡顿 |

### 7.2 可扩展性 (Scalability)

| 需求 | 策略 |
|------|------|
| 数据库 | 第一版 PostgreSQL，SQLAlchemy ORM 抽象层，切换数据库不改业务代码 |
| 图片存储 | 本地文件存储抽象为 `StorageService` 接口，后续替换为 OSS/S3 只需实现新适配器 |
| 前端 | 表示层与 API 层完全分离，后续可整体替换为 SPA |
| 文章内容类型 | `extra_fields` JSON 插件机制，新增内容类型不改表结构 |

### 7.3 安全性 (Security)

| 需求 | 说明 |
|------|------|
| 活码ID | 8 位随机字符串（大小写字母+数字），不可预测，防遍历 |
| 软删除 | 数据不物理删除，防止误操作导致数据丢失 |
| 图片上传 | 仅允许上传图片格式（jpg/png/webp/gif），限制单文件 < 10MB，防恶意文件上传 |
| XSS 防护 | 文章展示页渲染富文本时进行 HTML 转义/过滤，防止注入脚本 |
| 未来多用户 | 预留 JWT 认证 + 密码哈希（bcrypt）接口 |

### 7.4 可用性 (Usability)

| 需求 | 说明 |
|------|------|
| 文章展示页 | 移动端优先适配，扫码用户绝大多数使用手机 |
| 错误提示 | 友好提示页（活码停用、文章未发布、404），而非空白/报错页 |
| 二维码生成 | 配置变化后立即刷新预览，所见即所得 |

### 7.5 可维护性 (Maintainability)

| 需求 | 策略 |
|------|------|
| 分层架构 | API 路由层 → Service 业务层 → Repository 数据访问层，层间单向依赖 |
| 代码规范 | 遵循 PEP 8，类型注解覆盖所有函数签名 |
| 测试覆盖 | Service 层单元测试覆盖率 ≥ 80%，API 层集成测试覆盖核心路径 |
| 数据库迁移 | 所有表结构变更通过 Alembic 迁移脚本管理，禁止手动改表 |
| 日志 | 统一日志格式（时间+级别+模块+消息），扫码跳转关键路径打日志 |

### 7.6 兼容性 (Compatibility)

| 需求 | 说明 |
|------|------|
| 浏览器 | 扫码用户：Chrome/Safari 移动端最新主版本；管理员：Chrome/Edge/Firefox 桌面端最新主版本 |

## 8. 工程原则约束

以下软件工程原则贯穿本项目所有设计和实现决策，作为代码审查和架构评审的评判标准。

### 8.1 SOLID 原则

| 原则 | 在本项目中的应用 |
|------|-----------------|
| **S — 单一职责原则** (Single Responsibility) | 每个模块只负责一件事：`ArticleService` 只管文章，`QRService` 只管二维码，`StatsService` 只管统计。一个类 > 200 行或一个函数 > 50 行时需考虑拆解 |
| **O — 开闭原则** (Open/Closed) | 新增内容类型（地图、文件下载等）通过 `extra_fields` 扩展，不修改 Article 模型；新增目标类型通过 Resolver 注册，不修改路由逻辑 |
| **L — 里氏替换原则** (Liskov Substitution) | 子类/实现类必须可替换父类/接口而不影响正确性。例如 `StorageService` 接口的本地实现和 S3 实现必须行为一致 |
| **I — 接口隔离原则** (Interface Segregation) | Service 层提供细粒度方法，而非大而全的"上帝接口"。不强制调用方依赖不需要的方法 |
| **D — 依赖倒置原则** (Dependency Inversion) | 高层模块（API 路由）不依赖低层模块（数据库），双方都依赖抽象层（Service 接口） |

### 8.2 DRY (Don't Repeat Yourself)

- 数据库查询逻辑封装在 Service 层，API 路由不直接写 SQL/ORM 查询
- 二维码生成、图片处理等通用工具函数抽取为独立 Service 或 Utility
- 配置常量（尺寸映射、文件类型白名单等）集中管理，不散落在各模块
- **反例警告**：两个 API 接口做类似的查询时，必须抽取公共方法而非复制粘贴

### 8.3 KISS (Keep It Simple, Stupid)

- 第一版不做"可能会用到"的功能，只做当前版本明确需要的
- 优先选择最简单的实现方案：Jinja2 模板足够，不上 SPA；SQLite 足够，不上 PostgreSQL 集群
- 函数逻辑扁平化，避免超过 3 层嵌套
- 数据库查询优先用 ORM 方法，不用原生 SQL（除非性能关键路径经过 benchmark 验证需要优化）

### 8.4 YAGNI (You Aren't Gonna Need It)

- **不做**：第一版不做多用户、权限角色、文章版本管理、自定义域名、主题模板
- **但架构预留**：extra_fields、User 表、StorageService 接口、Resolver 模式——这些是"低成本预留、高成本补加"的点，提前预留合理
- **决策原则**：如果一个功能不确定是否将来会用，不做；如果明确知道将来会做但改造成本高，预留接口

### 8.5 关注点分离 (Separation of Concerns)

```
┌─────────────────────────────────────────────────────────┐
│  路由层 (API Router)     — 只负责：HTTP 请求/响应编解码    │
├─────────────────────────────────────────────────────────┤
│  服务层 (Service Layer)  — 只负责：业务逻辑、编排、校验    │
├─────────────────────────────────────────────────────────┤
│  数据访问层 (Repository) — 只负责：数据库 CRUD 操作抽象    │
├─────────────────────────────────────────────────────────┤
│  模型层 (Model)          — 只负责：数据结构和关系定义      │
└─────────────────────────────────────────────────────────┘
```

- 路由层不直接调用 ORM，必须通过 Service 层
- Service 层不直接操作 HTTP 对象（Request/Response），接收纯数据参数
- 数据访问层不包含业务逻辑，只做查询和持久化

### 8.6 最小惊讶原则 (Principle of Least Surprise)

- API 接口遵循 RESTful 命名规范：资源用复数名词，动作用 HTTP 方法（GET 查询、POST 创建、PUT 更新、DELETE 删除）
- 错误响应格式统一：`{"detail": "错误描述", "code": "ERROR_CODE"}`
- 分页接口统一使用 `?page=1&page_size=20` 参数，返回 `{"items": [...], "total": 100, "page": 1, "page_size": 20}`
- 时间格式统一使用 ISO 8601：`2026-08-17T15:30:00Z`

### 8.7 防御式编程 (Defensive Programming)

- 所有用户输入进行校验：文章标题非空、图片格式验证、二维码配置参数范围检查
- 外部依赖（文件系统、数据库）操作加 try-except，确保失败时有降级策略
- 数据库操作使用事务，避免部分写入导致数据不一致
- 关键路径（扫码跳转）使用后台任务异步记录日志，不阻塞主流程
